# 性能优化计划

这份文档记的是「现在有多快、慢在哪、按什么顺序修」。数字都是在本机实测
（AMD Ryzen 7 3800X，Windows 11，150% 缩放），复现命令写在每节末尾；改完之后
把这一节的数据换掉，别只写结论。

范围：`internal/` 与 `plugins/terminal` 的既有代码。终端渲染（软件光栅化）本身
没有低效算法，所以这里不动渲染路径，只修「白算的东西」和「每帧重复付的钱」。

## 1. 基线（改动之前）

| 项目 | 实测 | 怎么来的 |
| --- | --- | --- |
| 启动到首个窗口 | 165 ms | 记录 `NewWindow` 返回的时刻 |
| 输出吞吐 | 168.8 MB/s（1000 行彩色文本 473 µs） | `BenchmarkOutput` |
| 打字帧（每帧 1 字符） | 1.22 ms | 临时基准，见下 |
| 静帧（无变化） | 0.35 ms | 临时基准，见下 |
| 重绘帧（1600×1000@2x，61 行全变） | 6.37 ms | `BenchmarkFrame` |
| 内存 | 工作集 70 MB，私有 94 MB，40 线程 | 任务管理器 / `Get-Process` |
| 空闲（窗口可见） | 8.9–13.1% 单核 | 见第 5 节 |
| 空闲（最小化） | 0.2% 单核 | 同上 |
| 空闲（窗口 960×600 / 480×300 / 1800×1100） | 9.8% / 8.0% / 8.4% | 同上，与像素量几乎无关 |

CPU 剖析（`BenchmarkFrame`，21 秒样本）：`scene.SubpixelCoverage` 39.2%、
`raster.(*renderer).glyphs` 25.9%（累计 88.1%）、`raster.blendSubpixel` 16.8%、
`runtime.memmove` 6.0%、`raster.to8` 4.2%、`raster.clear` 4.4%。
字形查找（`internal/text.(*System).glyph`）只有 0.7%，说明缓存是有效的，
贵的是逐像素的覆盖率与混合——这是固有成本，不在本计划的修改范围内。

## 2. 要修的问题（按顺序）

每一步都独立、可单独提交、可单独验；不攒在一起改。

### S1 一帧一次 `GhosttyThemes()` —— 已做

- 位置：`internal/theme/scheme.go:37`（只为算 `make` 的 cap 调一次，结果全丢）、
  `internal/theme/scheme.go:51`（循环里再调一次）。
- 代价：每次是 `os.ReadDir(%LOCALAPPDATA%\ghostty\themes)` + 排序 617 个名字
  （比较函数里两次 `strings.ToLower`）+ Compact，约 24,000 次字符串分配，
  全在 UI 线程上。
- 修法：函数开头取一次放进局部变量，两处都用它。
- 验收：`BenchmarkUISchemes` 少一次目录读与排序；`go test ./...` 全绿。
- 已做：`internal/theme/scheme.go` 的 `Schemes` 开头 `ghostty := terminal.GhosttyThemes()`，
  cap 与循环都用它。配着 S2，这条路径现在只在文件写的方案变了时走一次。

### S2 配色列表按指纹缓存，不再每次重建 —— 已做

- 位置：`internal/app/apply.go:84`（无条件 `a.schemes = nil`）、
  `internal/app/settings.go:72`（`Schemes: a.schemeList()`）。
- 代价：实测 3.1 ms、757 KB、39,163 次分配，**每次设置改动都付一遍**——
  设置页编辑的是活 settings（`internal/app/settings.go:55`），拖一次滑块、
  点一次数字都会让 `apply()` 走完，所以是每帧付。
- 修法：`schemeList()` 自己记下 `s.Schemes` 的长度与首尾指纹，没变就不重建；
  `a.schemes = nil` 只留在真的换了列表的地方。
- 验收：设置页拖动时不再每帧付 3 ms；加一个测试断言「同一份设置连着要两次，
  第二次不重建」。
- 已做：`internal/store/settings.go` 的 `EqualSchemes`（名字不分大小写、颜色逐字节比）
  与 `internal/app/app.go` 的 `schemesFrom` 指纹；`schemeList()` 只在指纹变了时重建，
  `apply()` 里那行 `a.schemes = nil` 删掉了。指纹存的是 `Clone().Schemes`，
  免得页面就地改用户写的方案时指纹跟着变。测试：`TestEqualSchemes`、
  `TestSchemeListIgnoresOtherSettings`。

### S3 字体与配色没变就不碰终端 —— 已做

- 位置：`internal/app/apply.go:63-72`，每帧对所有标签的所有窗格
  `term.SetFont(font)` + `term.SetTheme(colors, nil)` + `SetCopyOnSelect` +
  `SetScrollMultiplier` + `SetMinimumContrast` + `setLinks`。
- 代价：与配色、链接无关的改动（透明度、语言、键位）也会全量下发。
- 修法：`applyWindow` 记住上一次下发的 `(字体, 配色, 复制选中, 滚动倍数, 对比度,
  链接)`，只重发变了的。
- 验收：只改 `backgroundOpacity` 时，终端的方法调用次数为 0（用测试替身计数）。
- 已做：`internal/app/apply.go` 的 `faceChange`/`faceChanges`（第一帧全发，之后逐项比），
  `App.faceSent` 记住是否已经全量发过；每个设置各管各的 `term.Set…`。
  测试：`TestFaceChanges`（只改透明度、语言时全 false；改字体、方案、主题时只真
  `colors`；链接那项真 `links`）。

### S4 录制快捷键的键表只生成一次 —— 已做

- 位置：原 `internal/ui/keybindings.go:406-419` 的 `capture`（16 种修饰 × 72
  个键 = 1152 次 `OnWindowShortcut`），放大器是 `internal/ui/keys.go:178` 的
  `FormatKey` 内部又调一次 `KeyNames()`——每帧 1,168 次键名表构建。
- 代价（实测，光标不动、停在录制态）：**1.39 ms/帧、2.38 MB/帧、59,248 次分配/帧**。
- 事实纠正：**不能「进入录制时绑一次就不动」**。窗口每帧都会
  `clear(rt.actions)`（`mygo/ui/context.go:125-126`），快捷键只活在声明它的那一帧，
  所以声明必须每帧重来；能省的是「造键表与闭包」这一步。
- 已做的修法：新增 `ui.Capture`（`internal/ui/keybindings.go`），键表与 1152 个
  记录闭包在录制第一帧造一次，之后每帧只把它们交给窗口；`app` 持有一个
  `a.capture` 从帧到帧传下去（`internal/app/app.go`、`internal/app/settings.go`）。
  顺手去掉 `KeyNames()` 里重名的键（`plus` 被列了两次，窗口本来也只当一个快捷键）。
- 实测：造键表 **1,696,395 ns/次、2,705,315 B、60,430 allocs**（每次录制一次）；
  之后每帧只剩 `Capture.ready` 的 **40 ns（1 alloc 是测试里的桩）** 与 1152 次
  声明。验收：`go test ./internal/ui/ -run TestCapture` 全绿
  （`TestCaptureMakesTheKeysOnce` 钉「只造一次 + 记录的是当前动作」，
  `TestCaptureKeysAreTheShortcuts` 钉「每条键仍按 `FormatKey` 的名字记录」）。

### S5 选了 Ghostty 方案时，预览按名字缓存 —— 已做

- 位置：`internal/ui/schemes.go:237-238`（页头预览）→ `internal/theme` →
  `mygo/plugins/terminal/ghostty.go:26-47`（`os.ReadFile` + 解析）。
- 代价：外观页停在某个 Ghostty 方案上时，每帧一次文件读；只有文件不存在才回落
  到内置表，所以常见路径就是读文件。默认的 `Campbell` 走内置 11 项表，不慢。
- 修法：按「方案名 + 文件修改时间」缓存解析结果。
- 验收：拖动滑块时不再有文件读（用一个计数或临时改名目录来验）。
- 已做：`internal/theme/scheme.go` 的 `named` 改成「查 `shipped` 缓存、复制一份」，
  `read` 才真的读文件或查内置表；缓存 64 项、满则清空。复制是必须的——`Scheme`
  会把颜色就地写进 `*terminal.Theme`。代价：运行中改的 Ghostty 主题文件，下次启动才生效。
  测试：`TestNamedSchemesAreCopies`（同名两次是两份、内容相同）、
  `TestCustomColorsStayOutOfTheCache`（文件写的颜色不进缓存）。

### S6 外观页每帧的线性扫描改查表 —— 已做

- 位置：`internal/ui/schemes.go:80-82`（`swatchOf` 对 624 项线性扫，调用点
  `:34`）；`internal/ui/fonts.go:63-65`（每帧为字体提示重建 `known`/`mono`
  两张 map，输入是全机字族）。
- 修法：`map[string]Scheme` 与「字族集合」各缓存一次，设置变了才重建。
- 另：`internal/app/font.go:91` 的 `myui.Shape(asciiPrintable, …)` 落在 UI 线程
  （注释自承首帧 23–26 ms），挪进 `ensureFontFamilies` 那个 goroutine。
- 验收：外观页首帧 < 10 ms；静帧不再分配（基准或 `-benchmem` 断言）。
- 已做：
  - `swatchOf` 查表：`SchemesCache` 加 `names`/`named`，`findScheme` 里「列表还是那份
    列表」用第一个元素的地址判断（`sameList`），不逐项比——逐项比 624 项要 2.5 µs，
    比它省下的线性扫还贵。实测 624 个名字：**2,476 ns → 52 ns**。
  - 字体提示的两张 map：`fontMaps` 以列表首元素地址为指纹缓存（`fontKnown`）。
  - `myui.Shape(asciiPrintable, …)` 挪进 `ensureFontFamilies` 的 goroutine，答案随
    `a.Do` 回 UI 线程（`text.System.Shape` 自己带锁，可以在别的 goroutine 上跑）。

### S7 把帧计数接出来，定位空闲开销 —— 读数已做并验证，归因仍待

- 已做：命令面板的「帧率」动作（`internal/action/action.go` 的 `Frames`）在右下角开一个读数，
  显示最近 240 帧的平均帧率、最低帧率与最长帧（`internal/app/frames.go` 的 `frameMeter`/`rate`，
  画在 `internal/ui/frames.go`，`ui.State.Frames` 传进去）。量的是窗口自己画的帧，所以空闲时不画帧，
  数字就停在最后一帧。没有默认键位：要常用就在「设置 → 操作」里绑一个。
- 实测（1200×760 窗口，空闲、光标闪）：平均 **66–72 fps**、最低 **34–51 fps**、
  最长帧 **19.8–29.5 ms**；启动后头一帧 200 ms 上下，会被 240 帧的窗口很快冲掉。
  这说明窗口确实在按刷新率画、且每隔几十帧就有一次掉到 30 fps 的帧——
  与第 5 节「空闲占一核 9%」是同一件事的两面。
- 测试：`internal/app/frames_test.go` 的 `TestRate`/`TestFrameMeter`（环形表与统计），
  `internal/ui/frames_test.go` 的 `TestFramesReadout`（三行数字都画出来、
  位置在 900×700 窗口的右下角、关掉时一个字都不画）。
- 仍待：`MYGO_FRAME_STATS` 在 wt-go 里没有出口（`log` 被 `internal/app/run.go:44-48` 接到
  `wt-go.log`，实测 0 字节），所以每帧各相位耗时还拿不到；空闲 9% 的归因停在第 5 节那一层
  （框架示例 0.0%、wt-go 9.1%、杀掉窗格里的 shell 后 6.6%、最小化 0.2%）。

## 5. 还没查清：空闲时那 9%

证据链（都是本轮实测）：

- `mygo examples/hello`（框架最小窗口）空闲 **0.0%**；
- `mygo examples/terminal`（真起 `pwsh` 的终端示例）空闲 **0.0%**；
- wt-go 空闲 **8.9–13.1%**；
- 把窗格里的 `pwsh` 杀掉之后仍有 **6.6%**（所以不是 shell 输出）；
- 最小化后 **0.2%**（与「窗口可见」强相关）；
- 窗口尺寸几乎不影响（见第 1 节），所以不是逐像素成本；
- 线程采样：6 秒内只有 2 个线程在跑（437 ms + 78 ms ≈ 7.3% + 1.3%）。

也就是说：wt-go 在窗口可见时有一份每秒几百次量级的固定工作，既不是 shell 输出，
也不是逐像素绘制。`MYGO_FRAME_STATS=0` 在真机上拿不到帧数——wt-go 把 `log` 接给了
`data/logs/wt-go.log`（`internal/app/run.go:44-48`），实测日志 0 字节，
`-RedirectStandardError` 也是空文件，所以这条统计路径等于哑的。

下一步（S7）：给帧统计一条能看见的出口（临时把 `MYGO_FRAME_STATS` 的输出直接写
stderr，或加一个只在开发时开的 `-debug-frames`），先拿到「帧率 + 每帧各相位耗时」，
再决定改谁。没有这一步，任何结论都是猜。

## 6. 不做的

- 不改软件光栅化的文字路径（95% 的 CPU 在那里，但那是固有成本，改它就是重写渲染器）。
- 不改 `mygo` 上游的行为（要改先在该 fork 里评估，并按 ADR-58 的形状同步）。
- 不为性能删掉用户可见的功能（命令面板的匹配、配色预览等）。
