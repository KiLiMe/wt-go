# 代码导读

wt-go 的代码地图：目录职责、包边界、渲染与生命周期、改动前必读的坑。路径一律相对仓库根。
用法见 [使用说明.md](使用说明.md)，取舍理由见 [decisions.md](decisions.md)，阶段状态见 [plan.md](plan.md)，
工程约定见 [../AGENTS.md](../AGENTS.md)。

## 目录

```text
wt-go/
├── main.go                 入口，一行 os.Exit(app.Run())
├── internal/
│   ├── app/                应用状态与动作：标签、窗格、设置读写、热重载、命令面板与查找栏的状态、进程生命周期
│   ├── ui/                 只画 State：标签栏（兼标题栏）、窗格、设置页、命令面板、查找栏、对话框
│   ├── action/             动作目录：id、标题、分组、默认键位（纯函数）
│   ├── fault/              故障码 E1xx/E2xx/E3xx 与一行含义（纯函数）
│   ├── cli/                不开窗口的部分：wt-go diag 的报告、wt-go mcp 的工具（纯函数，数据由 sys 读）
│   ├── mcp/                Model Context Protocol 服务器（JSON-RPC 2.0，只用标准库）
│   ├── pane/               窗格树与标签集合：切分、焦点、关闭补位（不做 IO）
│   ├── layout/             窗格树的几何计算（纯函数，不认识终端）
│   ├── profile/            profile 模型与自动发现结果的合并（纯函数）
│   ├── store/              settings.json 的解析、序列化、默认值、范围校验（纯函数）
│   ├── theme/              配色：设置里的方案 > 内置 > Ghostty 617 套（纯函数）
│   ├── sys/                全部 OS 副作用：路径、原子写、归档、日志、诊断读取、进程树与「还有程序在跑」的三态判断（含启动器 shim 的下探）、Job Object、shell 探测、打开路径、崩溃日志
│   └── i18n/               中英文案（缺条目回落原文）
├── resources/icon.png      图标源（1024×1024 PNG，go run ./tools/genicon 重新生成）
├── tools/genicon/          用 SDF 画 icon.png
├── build.ps1               日常构建：mygo 打包到 build\windows-amd64\wt-go.exe
├── mygo.json               go tool mygo build 的包名、版本与打包信息
├── docs/                   使用说明 / 故障排查 / 代码导读 / decisions（ADR）/ plan（阶段计划）
└── .github/workflows/      ci.yml（gofmt / vet / test / 打包；标签时同一个文件发布）
```

## internal/cli 与 internal/fault

| 文件 | 内容 |
| --- | --- |
| `fault/fault.go` | `Code` 与八个码、`Line`（写进日志的一行）、`Find`/`In`（从日志里认码） |
| `cli/cli.go` | `Run`：没参数就返回 `handled=false` 让窗口启动；`Usage` 常量与 `diag` 开关（`--json`、`--redact`） |
| `cli/report.go` | `Collect`：把版本、路径、原生库、shell、profile、检查项汇成 `Report`；`Text`/`JSON`/`Explain` |
| `cli/mcp.go` | 把同一份 `Report` 包成五个工具与两个资源，交给 `mcp.Serve` |
| `mcp/mcp.go` | JSON-RPC 2.0 循环、`Tool`/`Resource` 模型、参数取值辅助（`ArgString`/`ArgInt`/`ObjectSchema`） |

这条链路全部走 `internal/sys` 读现场，不打开窗口，也不认识 `ui`/`app`。
新加一个失败路径时：先在 `fault` 里加码，再在 `checks` 里加上对应的检查，最后写进
`docs/故障排查.md` —— 三处对齐了，`wt-go diag` 与文档才不会各说一套。

## internal/pane 与 internal/layout

- `pane.Node`：`Term` 非空即窗格，否则是 split（`First`/`Second`/`Share`/`Vertical`）。
- `pane.Tab`：`Root *Node` + `Focus *Node`；设置标签页的 `Root == nil`。
- `pane.Set`：窗口里的标签集合（`Tabs`、`Active`、`Front()`）。移除窗格时**返回**被移除的句柄，不关闭进程。
- `layout.Layout(root, rect)`：算出每个窗格与分割线的矩形。分割线 4dp，每个窗格至少 40dp，
  `Share` 在拖动时被夹在两端之内。

## 边界与链路

依赖方向自上而下，`app → ui → {pane, layout, store, theme, profile, action} → i18n`：

```text
main (根包)     → internal/app
internal/app    → action cli fault ui pane profile store theme i18n sys
internal/ui     → action pane layout profile store theme i18n (mygo/ui, mygo/plugins/terminal)
internal/cli    → fault mcp profile store sys
internal/theme  → store
internal/pane   → layout (mygo/plugins/terminal)
internal/profile→ store
internal/store  → action
internal/action → i18n
internal/mcp    → （无内部依赖）
internal/fault  → （无内部依赖）
internal/sys    → （无内部依赖；标准库与 golang.org/x/sys/windows）
internal/layout → （无内部依赖）
internal/i18n   → （无内部依赖）
```

`internal/app/deps_test.go` 用 `go list` 读每个包的直接 import 与这张表比对，
并检查 `action`/`cli`/`fault`/`i18n`/`layout`/`mcp`/`pane`/`profile`/`store`/`theme`/`ui` 不 import
`os`/`os/exec`/`path/filepath`/`io/fs`/注册表 —— 所以纯函数包做不了 IO，数据只能由 `app` 注入。

要点：

- `ui` 绝不 import `app` 或 `sys`：界面只画，动作经 `ui.Actions` 在 UI 线程上回调。
- `ui` 不认识终端：它按 `pane.Layout` 给的矩形摆位置，终端视图由 `app` 提供的 `Tab.Mount` 画。
- `pane` 不做 IO：`Set.Remove` 只把 `*terminal.Terminal` 交出来，`app` 负责 `Close()`。
- `action` 是动作名的唯一来源：键位、`▾`/右键菜单、命令面板、设置页标题都从它取。
- `cli` 与窗口是同一份 exe 的两张皮：`Run` 没参数才开窗；`cli` 只调 `sys` 读现场，
  所以 `wt-go diag` 与正在跑的窗口互不影响。
- **故障码只有一份**：`internal/fault` 的码 → `cli.checks` 判它 → `docs/故障排查.md` 解释它。
- 一个终端只能有一个 `terminal.View` 挂载点（libghostty 的约束）：窗格挂载点每帧重建，
  但 `Term` 句柄是同一个。

## 渲染流程

1. mygo 每帧调用根 `View` → `app.view(c)`：清理已关掉的对话框 → 记内容区 → `apply()`（把改动落到位）
   → `bind(c)`（挂键位）→ 组装 `ui.State` → `ui.View(c, st, a)`。
2. `ui.View` 从下到上：标签条（36dp，兼标题栏）→ 窗格树或设置页 → 覆盖层
   （重命名、确认、命令面板、查找栏）。
3. 状态只在 `app` 改；改完 `Invalidate()` 请求下一帧。终端的标题/退出回调经 `App.Do` 排回 UI 线程。
4. 键盘焦点每帧用 `Element.Focus()` 保持（`AutoFocus` 只在一帧生效）；命令面板/确认框开着时
   标签页不把焦点还给终端，查找栏开着时同样不还。

## 改动前必读

- **`AutoFocus` 只生效一帧**，移动焦点必须用 `Focus()`；焦点窗格每帧重新 `Focus()`。
- **`keybindings` 是整张表**：写了就完全取代默认值。默认键位来自 `action.All()`，
  改默认键只改 `internal/action`，不要另加一份。
- **键位录制以动作 id 为键**：设置页把 `action.All()` 的每个动作都列出来，`entry.row == -1`
  就是文件里没绑定，录一个新键时 `SetKeybinding` 会 `append` 一条。在 `action.All()` 里
  加一个动作，菜单、命令面板、设置页会自动多出它，不用改 `ui`。
- **标签宽度是量出来的**：`measuredName` 走 `Context.MeasureText`，夹在 `minTabName`–`maxTabName`
  之间，过长由 `Ellipsis("…")` 截。别再用写死的估算值。
- **`ui.Context.Shortcut` 会跳过已被焦点元素处理的键**：输入框吃掉 `Enter`（用 `in.Submitted()` 判断）
  与方向键时，别指望 `c.Shortcut(0, myui.KeyDown)` 还能收到。`OverlayShortcut` 是 `Element` 的方法，
  不是 `Context` 的。
- **`myui.Modal`/`DialogBase` 会在点背景或按 `Escape` 时把 `open` 置 false**：状态用 `*bool`
  绑给它，`app` 每帧看到 false 就丢弃这个对话框。
- **设置页改的是内存**：表单直接写 `a.settings`，每帧与 `a.applied` 比较后幂等应用；
  「保存」才写盘。profile 编辑用副本（`a.editing`），看一眼不会污染文件。
- **热重载以文件字节为准**：有未保存草稿时不覆盖；外部已改过时拒绝保存。
- **关窗格的进程要自己关**：`pane` 只交出句柄；`Terminal.Close()` 只能在 `app` 里调。
- **Windows 子进程收尾靠 Job Object**：`Run` 一开始把本进程加进 `KILL_ON_JOB_CLOSE` 的作业，
  之后所有 shell 自动继承，窗口崩了也不会留下 `pwsh.exe`。
- **坏配置要归档不能吞**：解析失败写 `settings.json.bad-<时间>`，原因给设置页看；
  写盘走临时文件 + 原子替换，保留原文件权限与软链接。
- **依赖表是测试**：新增包/改 import 必须同步 `deps_test.go` 与本文的依赖图，否则 `go test ./internal/app` 失败。
- **新的失败路径要编号**：`fault.Code` + `fault.Line`（日志）+ `cli.checks`（`diag`）+ `docs/故障排查.md`。
  日志行以时间戳开头，所以 `fault.Find` 是逐词找码，不是只看行首。
- **GUI 子系统没有控制台**：打包出来的 exe 带 `-H=windowsgui`，`log.Printf` 默认全丢；
  `app.Run` 先 `sys.OpenLog` 把日志接到 `wt-go.log`，新代码继续用 `log.Printf` 就对了。
- **Linux 的标题栏也自己画**（`titlebar_linux.go`）：`TitleBarHidden` + `HideWindowButtons: true` 让 GTK 不建
  `GtkHeaderBar`，标题栏与按钮都由 `ui/tabs.go` 画，桌面主题影响不到它；按钮的位置与顺序来自
  `Theme.WindowButtons()`（`gtk-decoration-layout`），合成器自己装饰时（KWin Wayland）为空、不画。
  同时 `c.TitleBar()` 归零，条带右侧让位区随之消失。
- **注释是英文、文档是中文**：与 mygo 上游一致。

## 构建与测试

```pwsh
pwsh .\build.ps1 -Test               # 构建到 build\windows-amd64\wt-go.exe（-Test 先跑 vet 与测试）
go vet ./internal/... ; gofmt -l .   # 提交前
go test ./internal/...               # 不含 race
go test -race ./...                  # CI 在 Linux 上跑这套
pwsh .\build.ps1 -Package            # 等于 go tool mygo build -platform windows/amd64 -skip-installer -o dist
go run ./tools/genicon               # 改了图标：重画 resources\icon.png
```

CI（`.github/workflows/ci.yml`，唯一的 workflow）在每次 push 与 PR 上跑 `gofmt`、`go vet`、
`go test -race`（Linux 跑整套与 race，Windows/macOS 跑不带 race 的同一套），并把两个平台的
便携包打出来、校验包内条目后上传为 artifact。打 `vX.Y.Z` 标签时，同一个文件里的 `release`
任务（`if: github.ref_type == 'tag'`）取这些 artifact 算 `SHA256SUMS` 并建发布：
`wt-go_<version>_windows-amd64_portable.zip`（`wt-go.exe` + `ghostty-vt.dll`）与
`wt-go_<version>_linux-amd64_portable.zip`（`wt-go` + `libghostty-vt.so` + `wt-go.desktop`），
两边都带 `LICENSE`。打包步骤只存在一份，CI 打出来的就是发布出去的；安装器与 `.deb`
不随发布走（`mygo build` 仍会照常产出，只是不上传）。标签名必须等于 `mygo.json` 的
`version`，否则打包前就报错退出。
