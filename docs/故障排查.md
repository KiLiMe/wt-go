# 故障排查

wt-go 把已知的失败都编了号：`E1xx` 是窗口起来之前，`E2xx` 是读 `settings.json`，
`E3xx` 是跑起来之后。这个文件是每个编号的正文——它是什么意思、怎么确认、改什么。

排查的顺序永远是：**先跑 `wt-go diag`，再看 `wt-go.log`，最后才看代码。**

---

## 1 三分钟拿到现场

```pwsh
# 1. 一次说完这台机器上 wt-go 的状态：版本、路径、库里、shell、profile、检查项
.\build\windows-amd64\wt-go.exe diag

# 2. 同一份报告，机器读的版本
.\build\windows-amd64\wt-go.exe diag --json

# 2b. 要贴到 issue 或聊天里时：把账号自己的路径换成 %USERPROFILE% 之类的占位符
.\build\windows-amd64\wt-go.exe diag --redact

# 3. 窗口自己说的话（打包后的窗口没有控制台，全写在这个文件里）
Get-Content "$env:LOCALAPPDATA\wt-go\wt-go.log" -Tail 50

# 4. 上一次崩溃（没有这个文件就说明没崩过）
Get-ChildItem "$env:LOCALAPPDATA\wt-go\crash-*.log" | Sort-Object Name -Descending |
    Select-Object -First 1 | Get-Content -Tail 60
```

`wt-go diag` 的每一行：

| 行 | 内容 |
| --- | --- |
| `wt-go <版本> <提交> <平台>` | 这个 exe 是哪次构建；`+dirty` 表示构建时工作区有改动 |
| `exe:` | 正在跑的 exe 的完整路径 |
| `settings:` | `settings.json` 在哪；解析失败时下一行是原因 |
| `native:` | 终端插件会加载的 `ghostty-vt.dll`；`not found` 就是 E102 |
| `profile:` | 合并后的 profile，`ok` / `missing` |
| `log:` / `crash:` | `wt-go.log` 与崩溃日志的位置 |
| `checks:` | 全部通过时是一行；有失败时逐个打印 `FAILED <编号> <细节>` |

退出码：`diag` 永远返回 0（"这台机器坏了"不是命令失败），参数写错返回 2。

`--redact` 把报告里的个人路径换成占位符：`%USERPROFILE%`、`%LOCALAPPDATA%`、`%APPDATA%`、
`%TEMP%`（Linux/macOS 上是 `~` 与 `$XDG_CONFIG_HOME`），报告仍然说得出是哪个文件，
但不再说明这台机器属于谁。它只改报告，不改磁盘上的任何东西；可以和 `--json` 一起用。

## 2 把问题交给 AI

wt-go 的失败都在本机，能看见的信息只有三样：**diag 报告、`wt-go.log`、崩溃日志**。
把这三样给一个 AI，比描述现象准确得多。有两条路：

### 2.1 直接贴（什么都不用装）

```
这是我 wt-go 的现场，帮我看是哪个故障码、怎么修：

<粘贴 wt-go diag --redact 的输出>

<粘贴 Get-Content "$env:LOCALAPPDATA\wt-go\wt-go.log" -Tail 50 的输出>
```

再把 `settings.json` 贴上去（它会含 profile 的命令行，不含密码）。

### 2.2 让 AI 自己读（MCP）

`wt-go mcp` 是一个 Model Context Protocol 服务器：JSON-RPC 2.0 走 stdin/stdout，
不需要端口、不需要网络，也不需要窗口开着。编辑器或 agent 配置里加一段：

```json
{
  "mcpServers": {
    "wt-go": {
      "command": "D:\\path\\to\\wt-go.exe",
      "args": ["mcp"]
    }
  }
}
```

它给的五个工具，读的都是同一份报告（和 `wt-go diag` 完全同源）：

| 工具 | 回答 |
| --- | --- |
| `wtgo_diag` | 失败项 + 每个编号的含义，纯文本，**先调这个** |
| `wtgo_status` | 同一份报告，JSON |
| `wtgo_settings` | `settings.json` 的位置、能否解析、语言/主题/配色/默认 profile/键位数 |
| `wtgo_profiles` | 这台机器的 shell，与合并后的 profile，以及每个能否真正启动 |
| `wtgo_log` | 崩溃日志的末尾（`lines` 默认 120，`path` 指定某一份） |

两个资源：`wtgo://diag`（文本）、`wtgo://status`（JSON）。

协议层在 `internal/mcp`，报告在 `internal/cli`，二者都不碰窗口：
`wt-go mcp` 与正在跑的 wt-go 互不影响。

## 3 故障码

### E101 一个 profile 都起不来

**意思**：`wt-go` 找得到 profile，但它们指向的程序都不在这台机器上。

**确认**：`wt-go diag` 的 `profile:` 行全是 `missing`，或 `E101` 的细节是 `0 profiles`。

**修**：Windows 上至少该有 `pwsh7`（PowerShell 7）、`powershell`、`cmd` 中的一个。
`diag` 的 `profile:` 行就是 `sys.Discover` 的结果，一个都没有说明这台机器的 PATH 或系统目录不正常
（`C:\Windows\System32` 被挪走、或 PATH 被覆盖）。自己写的 profile 命令写错了也会落到这里：
在 `settings.json` 的 `profiles[].command` 里写**绝对路径**最稳。

### E102 找不到 libghostty-vt

**意思**：终端由 `libghostty-vt` 解析字节流。它找不到，就一个终端都画不出来。

**确认**：`diag` 的 `native:` 是 `not found`。插件按这个顺序找：

1. 环境变量 `MYGO_GHOSTTY_VT` 指的文件；
2. 打包后的应用资源目录（`mygo build` 打的包）；
3. **exe 同目录**下的 `ghostty-vt.dll`；
4. 用户缓存 `%LOCALAPPDATA%\mygo\natives\<sha256>\ghostty-vt.dll`
   （`go build` / `go run` 打的程序，缺了就自己下载到这里）。

**修**：`go run .` 不行，多半是下载被墙或代理拦了：设好 `HTTPS_PROXY` 再跑一次，
或手动把 `ghostty-vt.dll` 放到 exe 旁边。从源码 `go build` 出的 exe 不带这个库，
第一次跑靠第 4 条自己下载；`go tool mygo build` 打的包才把它放进资源目录（第 2 条）。

### E103 设置目录不可用

**意思**：`%LOCALAPPDATA%\wt-go` 建不出来：`LOCALAPPDATA` 没设，或被权限/组策略挡住。

**确认**：`diag` 的 `settings:` 是 `not available`。

**修**：这是系统环境的问题，不是 wt-go 的。确认 `echo $env:LOCALAPPDATA` 有值，
并且能在里面建文件。

### E201 settings.json 不是合法的设置

**意思**：文件不是 JSON，或不是这个程序认识的 JSON。窗口仍会打开，用的是默认值。

**确认**：`wt-go diag` 的 `settings:` 行下面就是解析器原话（通常带行号）。
窗口里也能看到：设置页顶部那条提示以 `E201:` 开头。

**修**：文件被原样保留成了 `settings.json.bad-<时间>`（同目录），所以不会丢。
照着 `docs/使用说明.md` 第 6 节的字段表改，或删掉文件让 wt-go 重新生成一份。

### E202 某个字段超出范围

**意思**：JSON 合法，但值不可能实现（比如 `font.size` 是 400）。

**确认**：`diag` 的细节会点名，例如 `settings: font.size must be between 4 and 200`；
窗口设置页的提示以 `E202:` 开头。

**修**：按点名的字段改。范围表在 `docs/使用说明.md` 6.5。

### E203 某个键位读不出来

**意思**：`keybindings` 里有一条的 `key` 不是键名（`"ctrl+!"`、`"hyper+t"`、`"f13"`）。
**只有这一条被丢掉**，其余照常工作，所以症状是"某一个快捷键没反应"。

**确认**：`wt-go.log` 里有一行带 `E203`，后面是被丢掉的原字符串；
`wt-go diag` 的 `last fault:` 会把它抄出来。

**修**：键位字符串的语法是 `修饰键+…+键名`，修饰键 `ctrl` `shift` `alt` `win`（也认 `super` `meta` `cmd`），
键名是 `a`-`z`、`0`-`9`、`f1`-`f12`、`tab` `enter` `escape` `space` `backspace` `delete` `insert`
`home` `end` `pageup` `pagedown` `up` `down` `left` `right` `minus` `equal` `comma` `period`
`slash` `semicolon` `quote` `backslash`。

### E204 字体族不是等宽字体

**意思**：`font.family` 里的名字这台机器没有，或者不是等宽字体（`Segoe UI` 这类）。
终端按“可打印 ASCII 里最宽的字形”定格宽，比例字体里最宽的那个字会把每一格都撑大，
症状是**字距极宽、列对不齐、本该一行的话提前折行**（行高正常）。
窗口不报错：它改用系统的 `monospace` 画，并把这一行写进日志。

**确认**：`wt-go diag` 的 `last fault:` 是 `E204 … ("Cascadia Mono" is not monospace, drawing with "monospace")`。
想自己核对解析到了哪个字体：`fc-match "<settings 里的 family>"`（Linux），再和 `fc-match monospace`
对比——两次结果不同，说明这个名字没被解析成系统的等宽字体。

**修**：设置页「配置文件」页的字体栏从列表里挑（列表是这台机器上装了、并且量出来是等宽的族名），
或者改 `settings.json` 的 `font.family`：

1. `"monospace"` —— 跟随系统等宽，任何机器都有，不确定就写这个；
2. `"<想要的族名>,monospace"` —— 逗号列表取第一个装了的，写错或没装就落到等宽。

本机有哪些等宽族名，Linux 上 `fc-list :spacing=mono family | sort -u` 可列出。

改完不必重启（每秒看一次 `settings.json`）。

### E301 某个 shell 起不来

**意思**：profile 指向的程序不在这台机器上，或没有执行权限。点这个 profile 会得到一个空标签。

**确认**：`diag` 的 `profile:` 行里有 `missing`；`FAILED E301` 的细节列出是哪个。

**修**：改 `profiles[].command`，或删掉这个 profile。`wt-go.log` 里每次尝试都会有一行带
`E301`，后面是 `terminal.New` 的原话（`The system cannot find the file specified` 之类）。

### E302 窗口因为 panic 停掉

**意思**：程序崩了。窗口消失，栈在 `crash-<时间>.log` 里。

**确认**：`%LOCALAPPDATA%\wt-go` 下有新的 `crash-*.log`；`diag` 的 `crash:` 行与 `FAILED E302`。

**修**：把那个文件的前 40 行贴到 issue 里。第一行是时间，第二行是 panic 的值，
后面是栈。**这是 wt-go 的 bug，不是你配错了。**

### E303 读不到进程列表

**意思**：关标签前，窗口要读一遍机器上的进程，才知道标签里还有没有程序在跑。
这一次没读到（Windows 上是进程快照失败，Linux 上是 `/proc` 不可读，macOS 上是 `kern.proc.all` 失败），
于是关标签时问的是“无法判断这个标签里是否还有程序在运行”，而不是“程序还在运行”。

**确认**：`wt-go.log` 里有一行带 `E303`，后面是系统给的原话。

**修**：一般是权限或系统限制（受限账号、沙箱、容器里没挂 `/proc`）。
读到进程列表后提示自动恢复准确；在那之前，关标签总会问一次，除非把
`confirmClose` 设成 `never`。

### E304 没认出标签的 shell

**意思**：开标签时窗口会盯一眼自己的子进程，认下这次启动的 shell（记下 PID，用来判断“还有没有程序在跑”）。
这一次没认到：三秒内没等到子进程，或者关标签时这张标签仍然没有对应的 shell。
于是这张标签关的时候问的是“无法判断这个标签里是否还有程序在运行”。

**确认**：`wt-go.log` 里有带 `E304` 的行，后面写的是 `no child process appeared within …`
（启动时就放弃了）或 `a tab has no shell process`（关标签时仍然没有）。

**修**：一般是 shell 启动得比三秒还慢（第一次跑 `pwsh.exe`、杀软在扫、磁盘很慢）。
关掉那个标签重开一个就能认上；如果每次都出现，把 `wt-go.log` 那几行贴到 issue 里——
那是认领逻辑的问题，不是你的配置。在那之前，`confirmClose` 设成 `never` 可以免去提示。

### E305 找不到 fontconfig

**意思**：Linux 上，程序在开窗前给 fontconfig 追加一条规则（字体不要声明次像素顺序），
免得 mygo 把灰度抗锯齿的字形当成彩色字形（emoji）原样绘制，结果**文字发白、发绿，
浅色底与提示框上几乎看不清**。这一次没加成：进程里找不到 `FcConfigGetCurrent` /
`FcConfigParseAndLoadFromMemory`，也就是没有加载 fontconfig。
窗口照常打开，只是文字颜色可能又变成上面那样。

**确认**：`wt-go.log` 里有一行带 `E305`；`fc-match monospace` 有输出就说明这台机器装了 fontconfig。

**修**：装 fontconfig（Debian `fontconfig`，Fedora / Arch 同名）。它本来是 Pango 的依赖，
通常已经在；真缺了的话文字排版本身也会出问题。装上后重启程序即可，不用改设置。

## 4 文件都在哪

| 文件 | 位置 |
| --- | --- |
| 设置 | `%LOCALAPPDATA%\wt-go\settings.json` |
| 运行日志 | `%LOCALAPPDATA%\wt-go\wt-go.log`（超过 1 MiB 时，下次启动挪成 `wt-go.log.1`） |
| 崩溃日志 | `%LOCALAPPDATA%\wt-go\crash-<yyyyMMdd-hhmmss>.log` |
| 坏掉的设置副本 | `%LOCALAPPDATA%\wt-go\settings.json.bad-<yyyyMMdd-hhmmss>` |
| libghostty-vt | 见 E102 的四个位置 |

Linux 上对应的目录是 `$XDG_CONFIG_HOME/wt-go`（通常是 `~/.config/wt-go`）。

## 5 报 issue 时给什么

1. `wt-go diag` 的完整输出（或 `diag --json`）；
2. `wt-go.log` 的最后 50 行；
3. 有崩溃日志就给前 40 行；
4. 相关的 `settings.json` 片段（和这个现象有关的那几节就够）；
5. 什么操作之后出现的（切标签、开分栏、改设置、粘贴…）。

前四样能用一条命令攒出来：

```pwsh
.\build\windows-amd64\wt-go.exe diag > wt-go-report.txt
Get-Content "$env:LOCALAPPDATA\wt-go\wt-go.log" -Tail 50 >> wt-go-report.txt
```
