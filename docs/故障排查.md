# 故障排查

wt-go 把已知的失败都编了号：`E1xx` 是窗口起来之前，`E2xx` 是读 `settings.json`，
`E3xx` 是跑起来之后。这个文件是每个编号的正文——它是什么意思、怎么确认、改什么。

排查的顺序永远是：**先跑 `wt-go diag`，再看 `wt-go.log`，最后才看代码。**

---

## 1 三分钟拿到现场

```pwsh
# 1. 一次说完这台机器上 wt-go 的状态：版本、路径、库里、shell、profile、检查项
.\build\windows-amd64\wt-go.exe diag

# 2. 同一份报告，机器读的版本
.\build\windows-amd64\wt-go.exe diag --json

# 2b. 要贴到 issue 或聊天里时：把账号自己的路径换成 %USERPROFILE% 之类的占位符
.\build\windows-amd64\wt-go.exe diag --redact

# 3. 窗口自己说的话（打包后的窗口没有控制台，全写在这个文件里；
#    便携版在 exe 旁的 data\logs\wt-go.log，确切路径看 diag 的 log: 行）
Get-Content "$env:LOCALAPPDATA\wt-go\wt-go.log" -Tail 50

# 4. 上一次崩溃（没有这个文件就说明没崩过；便携版在 data\crashes\）
Get-ChildItem "$env:LOCALAPPDATA\wt-go\crash-*.log" | Sort-Object Name -Descending |
    Select-Object -First 1 | Get-Content -Tail 60
```

`wt-go diag` 的每一行：

| 行 | 内容 |
| --- | --- |
| `wt-go <版本> (packaged <版本>) <提交> <平台>` | 这个 exe 是哪次构建：前半是 build info，括号里是 `mygo.json` 宣布的发布版本（裸 `go build` 没有这一段）；`+dirty` 表示构建时工作区有改动 |
| `exe:` | 正在跑的 exe 的完整路径 |
| `portable:` | 只在便携版打印：文件所在的那个 `data` 目录；没有这一行就是安装版，文件在 `%LOCALAPPDATA%\wt-go`（ADR-83） |
| `settings:` | `settings.json` 在哪；解析失败时下一行是原因 |
| `native:` | 终端插件会加载的 `ghostty-vt.dll`；`not found` 就是 E102 |
| `conpty:` | 只在 Windows 打印：终端拿来建控制台的 `conpty.dll`（`MYGO_CONPTY` 指的那份、exe 旁 `conpty\` 那份，或旧布局里 exe 同目录那份）；说成「Windows 自己的控制台」时程序问的配色与鼠标不会回来（ADR-82、ADR-83）。关于页的「终端」一行显示同一件事 |
| `profile:` | 合并后的 profile，`ok` / `missing` |
| `log:` / `crash:` | `wt-go.log` 与崩溃日志的位置 |
| `checks:` | 全部通过时是一行；有失败时逐个打印 `FAILED <编号> <细节>` |

退出码："这台机器坏了"不是命令失败，所以 `diag` 照旧返回 0；只有参数写错返回 2，
`--json` 序列化出错返回 1。

`--redact` 把报告里的个人路径换成占位符：`%USERPROFILE%`、`%LOCALAPPDATA%`、`%APPDATA%`、
`%TEMP%`（Linux/macOS 上是 `~` 与 `$XDG_CONFIG_HOME`），报告仍然说得出是哪个文件，
但不再说明这台机器属于谁。它只改报告，不改磁盘上的任何东西；可以和 `--json` 一起用。
Windows 与 macOS 的文件名不分大小写，匹配也不分：环境变量里是 `C:\Users\Foo`、报告里写作
`c:\users\foo` 的路径一样会被换成占位符；Linux 上则按原样匹配，两种大小写就是两个文件。

## 2 把问题交给 AI

wt-go 的失败都在本机，能看见的信息只有三样：**diag 报告、`wt-go.log`、崩溃日志**。
把这三样给一个 AI，比描述现象准确得多。有两条路：

### 2.1 直接贴（什么都不用装）

```
这是我 wt-go 的现场，帮我看是哪个故障码、怎么修：

<粘贴 wt-go diag --redact 的输出>

<粘贴 Get-Content "$env:LOCALAPPDATA\wt-go\wt-go.log" -Tail 50 的输出>
（便携版换成 exe 旁 data\logs\wt-go.log；路径以 diag 的 log: 行为准）
```

再把 `settings.json` 贴上去（它会含 profile 的命令行，不含密码）。

### 2.2 让 AI 自己读（MCP）

`wt-go mcp` 是一个 Model Context Protocol 服务器：JSON-RPC 2.0 走 stdin/stdout，不需要端口、
不需要网络，也不需要窗口开着，读的是与 `wt-go diag` 同一份报告。编辑器或 agent 里配一段：

```json
{
  "mcpServers": {
    "wt-go": {
      "command": "D:\\path\\to\\wt-go.exe",
      "args": ["mcp"]
    }
  }
}
```

五个工具（先调 `wtgo_diag`）、两个资源、协议细节与隐私，见 [MCP.md](MCP.md)。

## 3 故障码

### E101 一个 profile 都起不来

**意思**：`wt-go` 找得到 profile，但它们指向的程序都不在这台机器上。

**确认**：`wt-go diag` 的 `profile:` 行全是 `missing`，或 `E101` 的细节是 `0 profiles`。

**修**：Windows 上至少该有 `pwsh7`（PowerShell 7）、`powershell`、`cmd` 中的一个。
`diag` 的 `profile:` 行就是 `sys.Discover` 的结果，一个都没有说明这台机器的 PATH 或系统目录不正常
（`C:\Windows\System32` 被挪走、或 PATH 被覆盖）。自己写的 profile 命令写错了也会落到这里：
在 `settings.json` 的 `profiles[].command` 里写**绝对路径**最稳。

### E102 找不到 libghostty-vt

**意思**：终端由 `libghostty-vt` 解析字节流。它找不到，就一个终端都画不出来。

**确认**：`diag` 的 `native:` 是 `not found`。插件按这个顺序找：

1. 环境变量 `MYGO_GHOSTTY_VT` 指的文件（**文件不存在就跳到下一条**，不会把一个空的路径当成找到了）；
2. 打包后的应用资源目录（`mygo build` 打的包）；
3. **exe 同目录**下的 `ghostty-vt.dll`；
4. 用户缓存 `%LOCALAPPDATA%\mygo\natives\<sha256>\ghostty-vt.dll`
   （`go build` / `go run` 打的程序，缺了就自己下载到这里）。

**修**：`go run .` 不行，多半是下载被墙或代理拦了：设好 `HTTPS_PROXY` 再跑一次，
或手动把 `ghostty-vt.dll` 放到 exe 旁边。从源码 `go build` 出的 exe 不带这个库，
第一次跑靠第 4 条自己下载；`go tool mygo build` 打的包才把它放进资源目录（第 2 条）。

### E103 设置目录不可用

**意思**：设置目录建不出来：安装版是 `%LOCALAPPDATA%\wt-go`（`LOCALAPPDATA` 没设，或被权限/组策略
挡住）；便携版是 exe 旁的 `data\config`（exe 所在的文件夹只读，例如解压在 Program Files 或只读盘）。

**确认**：`diag` 的 `settings:` 是 `not available`；有 `portable:` 行就是便携版。

**修**：安装版是系统环境的问题，不是 wt-go 的：确认 `echo $env:LOCALAPPDATA` 有值，
并且能在里面建文件。便携版就把整个文件夹换到可写的地方（桌面、`%USERPROFILE%` 下），
或者删掉 `data` 目录，让它回到安装版的位置。

### E201 settings.json 不是合法的设置

**意思**：文件不是 JSON，或不是这个程序认识的 JSON。窗口仍会打开，用的是默认值。

**确认**：`wt-go diag` 的 `settings:` 行下面就是解析器原话（通常带行号）。
窗口里也能看到：设置页顶部那条提示以 `E201:` 开头。

**修**：文件被原样保留成了 `settings.json.bad-<yyyyMMdd-hhmmss>`（同目录），所以不会丢。
照着 [配置参考.md](配置参考.md) 的字段表改，或删掉文件让 wt-go 重新生成一份。

### E202 某个字段超出范围

**意思**：JSON 合法，但值不可能实现（比如 `font.size` 是 400）。

**确认**：`diag` 的细节会点名，例如 `settings: font.size must be between 4 and 200`；
窗口设置页的提示以 `E202:` 开头。

**修**：按点名的字段改。范围表在 [配置参考.md](配置参考.md) 的第 4 节。

### E203 某个键位读不出来

**意思**：`keybindings` 里有一条的 `key` 不是键名（`"ctrl+!"`、`"hyper+t"`、`"f13"`）。
**只有这一条被丢掉**，其余照常工作，所以症状是"某一个快捷键没反应"。

**确认**：`wt-go.log` 里有一行带 `E203`，后面是被丢掉的原字符串；
`wt-go diag` 的 `last fault:` 会把它抄出来。

**修**：键位字符串的语法是 `修饰键+…+键名`。完整的键名表、别名与动作清单在
[键位.md](键位.md)：修饰键 `ctrl` `shift` `alt` `win`（也认 `control` `super` `meta` `cmd`），
键名是 `a`-`z`、`0`-`9`、`f1`-`f12`、`tab` `enter` `escape` `space` `backspace` `delete` `insert`
`home` `end` `pageup` `pagedown` `up` `down` `left` `right` `minus` `equal` `comma` `period`
`slash` `semicolon` `quote` `backslash`（另有别名 `return` `esc` `del` `ins` `pgup` `pgdn`）。

### E204 字体族不是等宽字体

**意思**：`font.family` 里的名字这台机器没有，或者不是等宽字体（`Segoe UI` 这类）。
终端按“可打印 ASCII 里最宽的字形”定格宽，比例字体里最宽的那个字会把每一格都撑大，
症状是**字距极宽、列对不齐、本该一行的话提前折行**（行高正常）。
窗口不报错：它改用系统的 `monospace` 画，并把这一行写进日志。

**确认**：`wt-go diag` 的 `last fault:` 是 `E204 … ("Cascadia Mono" is not monospace, drawing with "monospace")`。
想自己核对解析到了哪个字体：`fc-match "<settings 里的 family>"`（Linux），再和 `fc-match monospace`
对比——两次结果不同，说明这个名字没被解析成系统的等宽字体。

**修**：设置页「配置文件」页的字体栏从列表里挑（列表是这台机器上装了、并且量出来是等宽的族名），
或者改 `settings.json` 的 `font.family`：

1. `"monospace"` —— 跟随系统等宽，任何机器都有，不确定就写这个；
2. `"<想要的族名>,monospace"` —— 逗号列表取第一个装了的，写错或没装就落到等宽。

本机有哪些等宽族名，Linux 上 `fc-list :spacing=mono family | sort -u` 可列出。

改完不必重启（每秒看一次 `settings.json`）。

### E205 settings.json 写不进去

**意思**：把探测到的 shell 写进 `settings.json` 这一步失败了：目录不存在、没有写权限，
或者文件被另一个进程锁住。本次运行仍按内存里的列表工作（标签栏、`▾` 菜单都有），
但文件里没有这些条目，下次启动也不会再探测（探测只发生在写第一份文件时），
需要手动在设置页「高级」里点一次「重新探测」。

**确认**：`wt-go diag` 的 `settings:` 行给出的路径能不能写；日志里这一行长这样：
`E205 settings.json could not be written, so the profiles the window found are not in the file (...)`，
括号里是 `os` 的原话（`Access is denied.` 之类）。

**修**：给那个目录写权限（或删掉只读属性），重启一次；也可以手动把里面的 `profiles` 补上。

### E206 删不掉 settings.json

**意思**：点「重置」时 `os.Remove` 失败：文件被别的程序占着（编辑器、杀毒软件的实时扫描），
或者目录只读。窗口没有重启，什么都没变。

**确认**：日志里 `E206 settings.json could not be deleted (…)`，括号里是 `os` 的原话。

**修**：关掉正在使用这个文件的程序再点一次；或者自己删掉它再重启窗口（效果一样）。

### E207 重启失败

**意思**：「重置」已经把 `settings.json` 删了，但新窗口没起来（exe 被删/被占、无权执行）。
旧窗口还开着，`settings.json` 已经不在，所以下次手动启动就是默认值。

**确认**：日志里 `E207 the window could not start again after the settings were deleted (…)`。

**修**：手动再开一次 `wt-go.exe`；起不来的原因看括号里的原话（`The process cannot access the file` 之类）。

### E208 打不开目录

**意思**：「设置目录」「程序目录」按钮调用 `sys.OpenPath` 失败：Windows 上 `explorer.exe` 不在 PATH，
POSIX 上没有 `xdg-open`（macOS 上没有 `open`）。

**确认**：`which explorer.exe` / `which xdg-open` 有没有；日志里 `E208 the folder could not be opened (…)`。

**修**：装 `xdg-utils`（提供 `xdg-open`），或者自己按 `diag` 里的 `settings:` 路径手动打开。

### E209 打不开链接

**意思**：要打开的东西没打开：终端里点的一个路径或网址，或「关于」里的「项目主页」按钮。路径经
`sys.OpenPath`（Windows 走 `explorer.exe`，其他平台走 `xdg-open` / `open`），网址经 `sys.OpenURL`
（Windows 走 `ShellExecuteW`，它能报出「桌面没有程序处理这个协议」）。

**确认**：`which xdg-open` / `which open` 有没有；日志里 `E209 the link could not be opened (…)`。
「关于」对话框里也会直接显示这一行。Windows 上括号里的 `error 31` 就是「没有关联的程序」，
最常见的原因是 `HKCU\Software\Microsoft\Windows\Shell\Associations\UrlAssociations\https\UserChoice`
指向的 `ProgId` 背后那个 exe 已经不在了（浏览器用 Scoop 升级换了目录、或手动挪过位置）：
看 `HKCU\Software\Classes\<ProgId>\shell\open\command` 里的路径在不在。

**修**：在「设置 → 应用 → 默认应用」把 https 重新指定给浏览器（`UserChoice` 带 Hash，直接改注册表会被 Windows
重置）；Scoop 装的浏览器换过位置的话，重装一次让安装器重写关联。Linux / macOS 上装浏览器或 `xdg-utils`，
或者自己在浏览器里打开那个地址；桌面没关联这种文件时，在终端里点它开不了，换个能开的程序或在命令行里打开。

**注意**：终端里的路径不存在时不会记这一行，也不会弹窗——那是故意的，见 ADR-84。

### E210 打不开设置文件

**意思**：设置页底栏的「打开设置文件」调用 `sys.OpenPath` 打开 `settings.json` 失败：
桌面没有关联的编辑器（Linux 上常见），或 `xdg-open` / `open` 不在 PATH。
文件本身是存在的（按钮会先把它写出来），失败的只是打开它的那一步。

**确认**：日志里 `E210 settings.json could not be opened (…)`；设置页底栏也会显示这一行。

**修**：装一个编辑 JSON 的桌面程序或 `xdg-utils`，或者点同页「高级」里的「打开设置目录」自己打开文件。

### E211 某个 profile 没出现

**意思**：`settings.json` 的 `profiles` 里有一条的 `id` 是空的，或者与上面某条的 `id` 重名。这样的条目
`internal/profile` 会跳过，所以配置页里看不到它，程序也不会启动它。文件本身照用：其余 profile 都正常。

**确认**：`wt-go.log` 里 `E211 profiles[3].id is "cmd", which a profile above it has` 一行，方括号里是它在
`profiles` 数组里的下标（从 0 数）；`wt-go diag` 的 `profile:` 行只会列出活下来的那几个。

**修**：给每一条 `profiles[]` 一个不重复的 `id`（`cmd`、`pwsh-admin` 这种短名字就行；配置页新建或复制 profile 时
会自动给），然后重开窗口。

### E301 某个 shell 起不来

**意思**：profile 指向的程序不在这台机器上，或没有执行权限。点这个 profile 会得到一个空标签。

**确认**：`diag` 的 `profile:` 行里有 `missing`；`FAILED E301` 的细节列出是哪个。

**修**：改 `profiles[].command`，或删掉这个 profile。`wt-go.log` 里每次尝试都会有一行带
`E301`，后面是 `terminal.New` 的原话（`The system cannot find the file specified` 之类）。

### E302 窗口因为 panic 停掉

**意思**：程序崩了。窗口消失，栈在 `crash-<yyyyMMdd-hhmmss>.log` 里。

**确认**：`diag` 的 `crash:` 行与 `FAILED E302`；文件在安装版是 `%LOCALAPPDATA%\wt-go`，
便携版是 `data\crashes`。

**修**：把那个文件的前 40 行贴到 issue 里。第一行是时间，第二行是 panic 的值，
后面是栈。**这是 wt-go 的 bug，不是你配错了。**

### E303 读不到进程列表

**意思**：关标签前，窗口要读一遍机器上的进程，才知道标签里还有没有程序在跑。
这一次没读到（Windows 上是进程快照失败，Linux 上是 `/proc` 不可读，macOS 上是 `kern.proc.all` 失败），
于是关标签时问的是“无法判断这个标签里是否还有程序在运行”，而不是“程序还在运行”。

**确认**：`wt-go.log` 里有一行带 `E303`，后面是系统给的原话。

**修**：一般是权限或系统限制（受限账号、沙箱、容器里没挂 `/proc`）。
读到进程列表后提示自动恢复准确；在那之前，关标签总会问一次，除非把
`confirmClose` 设成 `never`。

### E304 没认出标签的 shell

**意思**：开标签时窗口会盯一眼自己的子进程，认下这次启动的 shell（记下 PID，用来判断“还有没有程序在跑”）。
这一次没认到：三秒内没等到子进程、终端在等到之前就结束了，或者关标签时这张标签仍然没有对应的 shell。
于是这张标签关的时候问的是“无法判断这个标签里是否还有程序在运行”。

**确认**：`wt-go.log` 里有带 `E304` 的行，后面写的是 `no child process appeared within …`
（三秒到了就放弃）、`the terminal ended before a child process appeared`（程序没起来或
当场退出，窗口立刻放弃）或 `a tab has no shell process`（关标签时仍然没有）。

**修**：`the terminal ended …` 那条通常是 profile 的命令写错、程序不在 PATH 里，或者
shell 一启动就退出——先看同一个标签里终端上打印了什么。其余一般是 shell 启动得比三秒
还慢（第一次跑 `pwsh.exe`、杀软在扫、磁盘很慢）。
关掉那个标签重开一个就能认上；如果每次都出现，把 `wt-go.log` 那几行贴到 issue 里——
那是认领逻辑的问题，不是你的配置。在那之前，`confirmClose` 设成 `never` 可以免去提示。

### E305 找不到 fontconfig

**意思**：Linux 上，程序在开窗前给 fontconfig 追加一条规则（字体不要声明次像素顺序），
免得 mygo 把灰度抗锯齿的字形当成彩色字形（emoji）原样绘制，结果**文字发白、发绿，
浅色底与提示框上几乎看不清**。这一次没加成：进程里找不到 `FcConfigGetCurrent` /
`FcConfigParseAndLoadFromMemory`，也就是没有加载 fontconfig。
窗口照常打开，只是文字颜色可能又变成上面那样。

**确认**：`wt-go.log` 里有一行带 `E305`；`fc-match monospace` 有输出就说明这台机器装了 fontconfig。

**修**：装 fontconfig（Debian `fontconfig`，Fedora / Arch 同名）。它本来是 Pango 的依赖，
通常已经在；真缺了的话文字排版本身也会出问题。装上后重启程序即可，不用改设置。

## 4 文件都在哪

安装版（没有 `data` 目录的那一份）：

| 文件 | 位置 |
| --- | --- |
| 设置 | `%LOCALAPPDATA%\wt-go\settings.json` |
| 运行日志 | `%LOCALAPPDATA%\wt-go\wt-go.log`（超过 1 MiB 时，下次启动挪成 `wt-go.log.1`） |
| 崩溃日志 | `%LOCALAPPDATA%\wt-go\crash-<yyyyMMdd-hhmmss>.log` |
| 坏掉的设置副本 | `%LOCALAPPDATA%\wt-go\settings.json.bad-<yyyyMMdd-hhmmss>` |
| libghostty-vt | 见 E102 的四个位置 |

Linux 上对应的目录是 `$XDG_CONFIG_HOME/wt-go`（通常是 `~/.config/wt-go`）。

便携版（exe 旁有 `data` 目录）同名文件都在 `data` 里：`data\config\settings.json`、
`data\config\window-state.json`、`data\logs\wt-go.log`、`data\crashes\crash-<...>.log`
（ADR-83，见[使用说明.md](使用说明.md) 第 2 节）。想知道这一份是哪种，看 `diag` 的 `portable:` 行。

## 5 报 issue 时给什么

1. `wt-go diag` 的完整输出（或 `diag --json`）；
2. `wt-go.log` 的最后 50 行；
3. 有崩溃日志就给前 40 行；
4. 相关的 `settings.json` 片段（和这个现象有关的那几节就够）；
5. 什么操作之后出现的（切标签、开分栏、改设置、粘贴…）。

前四样能用一条命令攒出来：

```pwsh
.\build\windows-amd64\wt-go.exe diag > wt-go-report.txt
Get-Content "$env:LOCALAPPDATA\wt-go\wt-go.log" -Tail 50 >> wt-go-report.txt
```

便携版把第二行的路径换成 exe 旁的 `data\logs\wt-go.log`（`diag` 的 `log:` 行写的就是它）。
